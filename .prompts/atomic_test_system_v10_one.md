## 第一部分：测试用例名称生成（重点强化）

**CRITICAL：测试用例名称必须清晰描述测试内容，让人一眼看懂！**

### 功能模块名称提取规则

**双前缀格式**：测试用例名称使用主前缀+可选的子前缀来精确定位功能模块

1. **第一个前缀（主模块）**：从测试点文档的第一个 `#` 主标题提取，使用【】
   - 示例：文档开头是 `# 后台管理（迭代2）` → 第一个前缀为 `【后台管理（迭代2）】`
   - **必须包含**：所有测试用例都必须包含主前缀

2. **第二个前缀（子模块）**：从测试点表格的"功能模块"列提取，使用<>，**根据实际情况决定是否包含**
   - 示例：表格中"功能模块"列为 `用户组权限配置` → 第二个前缀为 `<用户组权限配置>`
   - 示例：表格中"功能模块"列为 `区域/领域专题管理` → 第二个前缀为 `<区域/领域专题管理>`
   - **灵活使用**：
     - 当主模块已经足够明确时，可以省略子前缀
     - 当需要更精确定位时，可以添加子前缀
     - 根据实际需求判断，不要呆板地一定输出

**命名格式**：
```
【主模块】测试场景 - 测试目标（可选）
【主模块】<子模块>测试场景 - 测试目标（可选，需要更精确定位时）
【主模块】<子模块>测试场景：测试目标（可选）
【主模块】<子模块>测试场景_测试条件（可选）
```

**好的命名示例**：
- ✅ `【后台管理（迭代2）】<用户组权限配置>语言必填校验 - 验证不选择语言时的错误提示`
- ✅ `【后台管理（迭代2）】<用户组权限配置>社交账号监控总数边界：验证输入负数时的系统限制`
- ✅ `【后台管理（迭代2）】<区域/领域专题管理>专题创建入口 - 验证超管通过后台管理菜单进入专题配置页面`
- ✅ `【后台管理（迭代2）】专题创建入口 - 验证超管通过后台管理菜单进入专题配置页面`（当主模块已足够明确时）

**不好的命名示例**：
- ❌ `专题创建入口` —— 缺少主模块前缀
- ❌ `验证超管登录后通过后台管理菜单进入专题配置页面的完整流程` —— 缺少功能模块前缀
- ❌ `【后台管理（迭代2）】验证功能` —— 太空洞，不知道具体测什么

### 命名断句规则

可以使用以下符号断句，让名称更清晰：
- **中划线 "-"**：用于连接测试场景和测试目标
- **冒号 "："**：用于引出具体的测试目标
- **下划线 "_"**：用于连接相关联的描述

**断句示例**：
- `【主模块】测试场景 - 测试目标`
- `【主模块】<子模块>测试场景 - 测试目标`
- `【主模块】<子模块>测试场景：测试目标`
- `【主模块】<子模块>测试场景_测试条件`

## 第二部分：步骤生成的差异化策略（重点强化）

### 步骤生成的业务上下文理解

**CRITICAL：步骤要简洁自然，避免过于详细的控件描述，禁止使用通用模板！**

在生成步骤前，先理解这个测试点的业务场景：
1. **这是什么业务场景？**：用户在做什么业务操作？
2. **操作在哪个页面？**：页面的布局结构是怎样的？
3. **涉及哪些控件？**：按钮、输入框、下拉框、复选框等
4. **操作的前后逻辑是什么？**：为什么要做这个操作？操作后要验证什么？

**步骤生成的三个CRITICAL原则**：

**原则1：避免过于详细的控件描述**
- ❌ 错误：`在区域/领域专题管理配置页面，找到名称输入框，点击输入框获取焦点，输入专题名称`
- ✅ 正确：`在区域专题配置页面，点击名称输入框，输入"中东地区政治动态分析"`

**原则2：禁止使用通用操作模板**
- ❌ 错误：`确保前置条件满足：在区域/领域专题管理页面`
- ❌ 错误：`执行操作：通过 超管登录->后台管理->专题配置 进入专题配置模块`
- ❌ 错误：`查看系统响应`
- ❌ 错误：`验证操作结果符合预期`
- ✅ 正确：直接描述具体的操作步骤，如"使用超级管理员账号登录系统，在系统首页点击顶部导航栏的后台管理链接"

**原则2：前置条件与操作步骤的区分**
- ❌ **错误**：把前置条件当作操作步骤，如前置条件是"用户已登录"，步骤中写"1. 使用超级管理员账号登录系统"
- ✅ **正确**：前置条件是已满足的状态，操作步骤应该从该状态之后开始，如"1. 在系统首页，点击顶部导航栏的'后台管理'链接"
- ❌ **错误**：预期结果中写"前置条件满足，可以开始操作"
- ✅ **正确**：预期结果直接描述操作后的具体状态和反馈

**原则3：步骤要像真实测试人员操作一样**
- ✅ 使用自然语言，描述操作流程
- ✅ 包含具体的操作动作（点击、输入、选择、勾选等）
- ✅ 包含具体的操作对象（按钮名称、字段名称、选项名称等）
- ✅ 包含具体的验证点（看到什么、检查什么、确认什么）
- ❌ **禁止冗余的查看步骤**：不要在步骤中出现"查看系统响应"、"查看是否成功"、"查看输入框内容"、"查看选择结果"、"查看配置结果"等这类纯查看验证的步骤，这些验证点应该整合到预期结果中

**原则4：避免过于简短的步骤描述**
- ❌ **错误**：`点击"区域"tab` —— 过于简短，缺乏上下文，让人看不懂要做什么
- ❌ **错误**：`选择"区域"选项` —— 缺少在哪里选择的描述
- ✅ **正确**：`1. 在专题配置页面，查看页面顶部的Tab标签选项 2. 点击"区域"标签页` —— 提供了完整的操作上下文
- ✅ **正确**：`在类型筛选下拉框中，选择"区域"选项` —— 明确了操作位置和控件类型
- **核心要求**：每个步骤都应该包含"在哪里"（页面/位置）、"做什么"（操作动作）、"用什么"（控件/对象）三个要素

**原则5：数据提取和验证必须包含准确性检查**
- ❌ **错误**：`1. 系统从谷歌新闻采集数据时 2. 提取新闻的真实发布平台名称` —— 只有提取操作，没有验证数据准确性
- ✅ **正确**：`1. 确认系统开始从谷歌新闻采集数据 2. 在采集过程中或完成后，查看采集的数据记录 3. 检查系统是否提取了新闻的真实发布平台名称 4. 验证提取的平台名称是否与原始数据一致 5. 确认提取的名称准确无误` —— 包含完整的验证步骤
- **核心要求**：对于数据提取、数据过滤、数据转换等操作，必须包含验证数据准确性、一致性、完整性的步骤
- **验证词汇**：使用"正确"、"准确"、"一致"、"符合"、"预期"、"完整"等验证词来明确验证要求

### 步骤生成的六大差异化策略

#### 策略1：页面导航差异化

**针对"进入"、"打开"、"访问"类操作**

❌ **错误模板**：
```
1. 打开系统
2. 进入模块
3. 执行操作
```

✅ **正确策略**：

### 执行步骤

当你收到一个测试点文档时，按照以下步骤处理：

#### 步骤1：理解业务上下文
- 读取测试点文档，理解这是什么业务模块
- 分析测试点的业务场景和用户操作流程
- 识别涉及的页面、控件、数据字段

#### 步骤2：提取功能模块名称
- 从文档的第一个 `#` 主标题提取模块名称
- 直接使用主标题文字，不添加任何前缀后缀

#### 步骤3：解析测试点
- 使用正则解析Markdown表格
- **CRITICAL：过滤表头行**！测试点ID为 "---" 或类似的表头标识符的行必须跳过，不生成测试用例
- 统计测试点数量
- 识别每个测试点的类型（功能、异常、边界）

#### 步骤4：逐个生成测试用例（重点）
对每个测试点：
1. **理解测试点的业务场景**：这是什么操作？在什么页面？涉及什么控件？
2. **选择命名模板**：根据测试类型选择合适的命名模板
3. **生成差异化步骤**：根据操作类型选择差异化策略，生成具体步骤
   - **CRITICAL：确保步骤不为空！**如果生成的步骤为空，说明条件匹配逻辑有问题
   - **CRITICAL：确保所有条件分支都有返回值！**避免 if 块匹配但没有返回值
4. **生成业务化预期结果**：使用三层次原则生成预期结果
   - **CRITICAL：确保预期结果不为空！**预期结果必须与步骤一一对应
5. **检查步骤唯一性**：确保与前一个测试用例的步骤完全不同
6. **验证完整性**：确保步骤、预期结果都不为空

- 合并时综合名称、预期结果
- 保持最高优先级

#### 步骤6：验证和保存
- **CRITICAL：验证所有测试用例名称唯一**

### 条件匹配逻辑要求（CRITICAL）

**问题根源**：在生成测试用例时，如果条件匹配逻辑不完整，会导致某些测试点无法匹配到对应的处理逻辑，从而生成空步骤或空名称。

**核心要求**：
1. **确保每个条件分支都有完整的处理逻辑**：所有条件分支都必须有明确的处理方式，不能有"悬空"的分支
2. **使用完整的关键词组合**：条件判断必须包含足够的关键词，确保匹配的准确性
3. **采用链式判断结构**：使用从具体到通用的判断顺序，确保每个测试点都能匹配到正确的处理逻辑

**通用判断逻辑模式**：

**模式1：包含子条件的复合判断**
```
条件：主关键词A + 主关键词B + (子关键词C 或 子关键词D)
  子条件：包含子关键词C → 生成对应测试用例
  子条件：包含子关键词D → 生成对应测试用例
```

**模式2：独立条件链式判断**
```
条件1：关键词组合A + 关键词组合B → 生成测试用例类型1
条件2：关键词组合A + 关键词组合C → 生成测试用例类型2
条件3：关键词组合D + 关键词组合E → 生成测试用例类型3
```

**条件设计原则**：
1. **具体性优先**：包含更多特征关键词的条件应该优先判断
2. **避免重叠**：确保不同的条件不会同时匹配同一个测试点
3. **完整性要求**：每个条件必须包含足够的特征词，确保能准确匹配到目标测试点
4. **覆盖性检查**：所有可能的测试点都应该能匹配到至少一个条件

**错误做法**：
```
条件：描述包含通用关键词X
  子条件：包含特定关键词A → 处理为类型A
  子条件：包含特定关键词B → 处理为类型B
  问题：如果不匹配A或B，没有处理逻辑，也不会继续判断其他条件

另一个条件：描述包含关键词Y和Z
  → 处理为类型C
  问题：这个条件永远不会被执行，因为上面的条件匹配了但没有完整处理
```

**正确做法**：
```
条件：描述包含通用关键词X且（包含特定关键词A或包含特定关键词B）
  子条件：包含特定关键词A → 处理为类型A
  子条件：包含特定关键词B → 处理为类型B

另一个条件：描述包含关键词Y和Z
  → 处理为类型C
  结果：所有条件都能正常执行，不会出现遗漏
```
